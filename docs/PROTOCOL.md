# Протокол HID-дисплея 1st Player RT5 / RT7 / RT9

Це практична документація до 64-байтного HID-протоколу, який використовують скрипти репозиторію. Вона зібрана з USB-снифів вендорського застосунку та експериментів на реальній панелі. Протокол неофіційний: виробник може змінити його в нових ревізіях.

## 1. Пристрій

| Параметр | Значення |
|---|---|
| Клас | USB HID, vendor-defined |
| Endpoint | Interrupt OUT, 64 байти |
| Вузол Linux | `/dev/hidraw*`, стабільний symlink `/dev/1stplayer-rt-lcd` |
| Тестовий USB ID | `5131:2007` |
| Швидкість кадрів | 1 Гц для телеметрії; до 200 Гц у стрес-тесті |

На тестовій машині пристрій з'явився як `/dev/hidraw3`. У твоїй системі номер може бути іншим. Репозиторій містить udev-правило, яке створює symlink `/dev/1stplayer-rt-lcd`; саме його використовує systemd-сервіс. Для ручного запуску можна передати як symlink, так і конкретний `hidraw`-вузол.

Скрипти визначають пристрій автоматично: явний аргумент → `/dev/1stplayer-rt-lcd` → пошук у `/sys/class/hidraw/hidraw*/device/uevent` за `HID_ID=0003:00005131:00002007`. Якщо збігів немає або їх кілька, скрипт показує список доступних `hidraw`-пристроїв і завершується, не надсилаючи кадри на випадковий вузол.

Перевірити, який саме вузол належить дисплею:

```bash
lsusb
udevadm info -q property -n /dev/hidraw3 | grep -E 'ID_VENDOR_ID|ID_MODEL_ID|HID_NAME'
cat /sys/class/hidraw/hidraw3/device/uevent | grep HID_ID
ls -l /dev/hidraw* /dev/1stplayer-rt-lcd
```

## 2. Кадр

Один кадр — **рівно 64 байти**. Він записується одним системним викликом `write()`:

```python
with open("/dev/1stplayer-rt-lcd", "wb") as dev:
    dev.write(frame)
    dev.flush()
```

Дисплей не надсилає ACK і не вимагає читання відповіді. Наступний кадр просто замінює попередній.

### 2.1. Структура

| Байт | Діапазон | Значення | Опис |
|---:|---|---|---|
| 0 | 1 байт | `seq` | Лічильник кадрів |
| 1 | 1 байт | `0x00` | Фіксований заголовок |
| 2 | 1 байт | `0x02` | Фіксований заголовок |
| 3–23 | 21 байт | `0x00` | Зарезервовано; скрипти пишуть нулі |
| 24–39 | 16 байт | `0x00`* | Службові та статичні іконки |
| 40–52 | 13 байт | бітмапа | Цифри, смужки, підписи |
| 53–63 | 11 байт | `0x00` | Зарезервовано |

\* У кадрах вендорського застосунку ці байти містять базовий стан іконок, наприклад:

```text
fd 08 08 08 fd 08 dd 0f d0 df 8f 00 00 00 00 00
```

Скрипти `lcd.py` і `lcd_sym.py` пишуть тут нулі, тому частина статичних іконок може бути неактивною. `unlock.py` пише `0xFF` у байти 24–53, щоб увімкнути все, що можливо.

### 2.2. Лічильник `seq`

Стартове значення — `0x61` (97). Далі лічильник інкрементується на 1 по модулю 256:

```python
seq = 0x61
...
frame[0] = seq
seq = (seq + 1) & 0xFF
```

У вендорських кадрах також видно послідовні значення `0x61`, `0x62`, `0x63`, … Тому лічильник, імовірно, використовується для перевірки свіжості кадру або просто для діагностики. Скрипти завжди інкрементують його.

### 2.3. Порядок бітів

Біти в кожному байті нумеруються з молодшого:

| Маска | Біт |
|---:|---:|
| `0x01` | 0 |
| `0x02` | 1 |
| `0x04` | 2 |
| `0x08` | 3 |
| `0x10` | 4 |
| `0x20` | 5 |
| `0x40` | 6 |
| `0x80` | 7 |

Приклад: увімкнути сегмент `A` першої цифри CPU — це байт 40, біт 0:

```python
frame[40] |= 0x01
```

## 3. Бітмапа сегментів

Байти 40–52 містять усі керовані елементи панелі:

- 6 цифр × 7 сегментів;
- 2 смужки × 10 поділок;
- підписи `CPU`, `GPU`, `%`, `°C`, `USAGE`.

Повна таблиця «байт → біт → функція» та карта цифр/смужок — у [`SEGMENT_MAP.md`](SEGMENT_MAP.md).

Коротко:

| Елемент | Адреси |
|---|---|
| Цифри CPU1–CPU3 | байти 40, 42, 44, 46, 48, 50, 52 (біти 0–2) |
| Цифри GPU1–GPU3 | байти 40, 42, 44, 46, 48, 50, 52 (біти 3–5) |
| Смужка CPU | байти 40–52, біт 6 |
| Смужка GPU | байти 40–52, біт 7 |
| Підписи | байти 41, 43, 45, 47, 49, 51 |

> У `CPU2` сегменти `D` і `G` розділені: `D = 46.1`, `G = 46.2`. Це не помилка і не дубль.

## 4. Приклад кадру

Кадр для стану:

- CPU: **65 °C**, **80%**;
- GPU: **42 °C**, **50%**;
- увімкнені підписи `CPU`, `GPU`, `USAGE`, `°C`.

```text
00  61 00 02 00 00 00 00 00 00 00 00 00 00 00 00 00
10  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
20  00 00 00 00 00 00 00 00 b6 05 d6 05 a4 03 76 06
30  62 01 62 05 56 00 00 00 00 00 00 00 00 00 00 00
```

Тут:

- `b6 05 d6 05 a4 03 76 06` — байти 40–47;
- `62 01 62 05 56` — байти 48–52;
- решта — нулі.

Цей кадр можна відтворити без сенсорів:

```python
import time

frame = bytearray.fromhex(
    "61 00 02 00 00 00 00 00 00 00 00 00 00 00 00 00"
    "00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00"
    "00 00 00 00 00 00 00 00 b6 05 d6 05 a4 03 76 06"
    "62 01 62 05 56 00 00 00 00 00 00 00 00 00 00 00"
)
with open("/dev/1stplayer-rt-lcd", "wb") as dev:
    dev.write(frame)
```

> Якщо дисплей не показує нічого, перевір шлях пристрою та права доступу. Якщо показує сміття — можливо, у твоєї ревізії інша карта сегментів. Замість symlink можна вказати конкретний `/dev/hidrawN`.

## 5. Службові біти

Під час ручного перебору бітів спостерігалися такі ефекти:

| Адреса | Ефект |
|---|---|
| 24.0 | зображення зникає |
| 30.6 | екран мигає |

Це не частина основного API, але корисно знати, чому `unlock.py` з `0xFF` у байтах 24–53 може давати нестандартну поведінку. Не використовуй ці біти у звичайних кадрах без потреби.

## 6. Сумісність і обмеження

- Протокол перевірено на панелі з USB ID `5131:2007`.
- Інші корпуси серії RT5/RT7/RT9 можуть мати іншу ревізію контролера.
- Невідомі байти краще залишати нулями, якщо ти не впевнений у їхньому призначенні.
- `unlock.py` — єдиний скрипт, який навмисно чіпає службові байти.
- Вендорське ПЗ для Windows не входить у репозиторій; посилання на офіційний завантажувач є в README.

## 7. Як зняти власну карту

1. Підключи дисплей і визнач його `hidraw`-вузол.
2. Візьми безпечний кадр-заготовку: `61 00 02` + 61 нуль.
3. По черзі виставляй один біт у байтах 40–52 і записуй, що засвітилося.
4. Не чіпай байти 24–39, поки не переконаєшся, що вони безпечні.
5. Зберігай результати у форматі `байт.біт → елемент`, як у [`SEGMENT_MAP.md`](SEGMENT_MAP.md).

Мінімальний приклад для одного біта:

```python
import time

for byte, bit in [(40, 0), (40, 1), (40, 2)]:
    frame = bytearray(64)
    frame[0] = 0x61
    frame[1] = 0x00
    frame[2] = 0x02
    frame[byte] |= 1 << bit
    with open("/dev/1stplayer-rt-lcd", "wb") as dev:
        dev.write(frame)
    time.sleep(1.0)
```

Після кожного кадру дисплей тримає стан, поки не прийде наступний. Тому для «блимання» треба надіслати кадр з увімкненим бітом, почекати, а потім надіслати нульовий кадр.
